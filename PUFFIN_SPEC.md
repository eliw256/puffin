# Puffin — Spec v0.1

> An engineer-first, AI-powered schematic, PCB, and firmware IDE.
> The engineer is the architect. The AI is the contractor. Puffin is the job site: the shared tools, the truth, and the inspections.

This document is written for Claude Code (or any coding agent) building Puffin. Read it fully before writing code. Build milestones **in order**; each one must pass its acceptance criteria before the next begins.

---

## 1. Product thesis

Puffin is for engineers who already know how to design a system and want to spend their time designing, not doing clerical work. They describe and manipulate the system at the block/pin/net level; Puffin keeps every representation (schematic, firmware config, diagrams) consistent and verified, and gives any AI model the tools and context to do the judgment-heavy work.

**Not for beginners.** Low friction for experts, granular control whenever they want it.

**Bring your own intelligence.** Puffin does not ship a model. It exposes its project, docs, and tools to whatever model the user brings, primarily via an MCP server. Puffin's value is the harness: the source of truth, the generators, the checks, the docs library, the visuals, and hardware-in-the-loop feedback.

---

## 2. Core design rules (non-negotiable)

1. **One source of truth.** A single, human-readable, diffable project graph (`puffin.yaml`) holds components, pins, nets, peripheral assignments, constraints, and design intent. Every other artifact is derived from it or imported into it.
2. **Deterministic sync; AI for judgment.** Propagating a change (e.g. a pin move → firmware `#define`) is done by deterministic code, never by an LLM. The AI is used for tasks that need judgment (e.g. rewriting a driver when a sensor moves from SPI to I2C). Same input must always produce byte-identical output.
3. **Every edit goes through one API.** The UI, the CLI, and the AI (via MCP) all mutate the graph through the same validated core API. No side doors. Invalid edits are rejected with a clear reason.
4. **Verification checks both humans and AI.** After any edit, validation runs. Errors block generation; warnings are surfaced.
5. **The engineer can override anything** — with an explicit, recorded override (e.g. `allow: strapping_pin` with a note), never silently.
6. **Generated files are marked and never hand-edited.** Header comment: `AUTO-GENERATED by Puffin from puffin.yaml — do not edit`.
7. **Interop over reinvention.** Schematic and PCB files are KiCad files. Puffin does not build a schematic editor or PCB layout engine in v0.
8. **Connectivity, not geometry.** The graph stores components, pins, nets, and intent. Copper geometry (traces, placement) stays in KiCad.

## 3. Scope

### In scope for v0 (the "wedge": the schematic ↔ firmware seam)
- Project graph schema, load/save, validation
- Part library format + an initial ESP32-S3 definition
- KiCad schematic → graph import (connectivity)
- Graph → firmware pin config generation (ESP-IDF C header first)
- Pin/peripheral legality checks against part definitions
- MCP server exposing the graph, checks, generators, and docs
- Local web UI: color-coded pin map + simple block diagram
- Hardware-in-the-loop (HIL): serial telemetry + logic-analyzer timing check

### Explicitly out of scope for v0 (parked; do not build)
- PCB layout or autorouting
- Generating/placing full KiCad schematics from the graph (v1: write-back of net/label changes)
- Photo-based board reverse engineering (v3+)
- BOM sourcing and pricing
- Circuit simulation (SPICE)
- Bundled AI model or chat UI as the primary interface

## 4. Architecture

```
            ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
            │   Web UI     │   │     CLI      │   │  MCP server  │ ← user's own AI model
            └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
                   └──────────────────┼──────────────────┘
                                      ▼
                          ┌───────────────────────┐
                          │     puffin-core       │
                          │  graph API + validate │
                          └───┬───────┬───────┬───┘
                ┌─────────────┘       │       └──────────────┐
                ▼                     ▼                      ▼
        Importers (KiCad)     Generators (firmware)    HIL (serial, sigrok)
                                      │
                               Part/doc library
```

**Headless core first.** The core library + CLI + MCP server must be fully usable with no UI. The UI is a client of the core, never the other way around.

### Recommended stack (confirm before M0; see §11)
- **Core:** Python 3.12+, `pydantic` v2 for schema/validation, `ruamel.yaml` (preserves comments/order for clean diffs)
- **KiCad import:** `kicad-cli sch export netlist` (KiCad 8+), parsed in Python; `kiutils` as fallback for reading symbol/pin details
- **MCP:** official MCP Python SDK
- **HIL:** `pyserial`; `sigrok-cli` via subprocess for logic analyzer capture
- **Web UI:** FastAPI backend serving a Svelte or React (Vite, TypeScript) frontend; runs locally
- **Tests:** `pytest`, golden-file tests for all generators
- **Packaging:** `uv`; single entry point `puffin`

### Repo layout
```
puffin/
  core/          graph model, load/save, edit API, validation
  library/       part definition loader + bundled parts
  importers/     kicad/
  generators/    espidf/

  mcp/           MCP server
  cli/           `puffin` command

examples/        example projects incl. a dual-ESP32-S3 board
tests/
```

## 5. Data model

### 5.1 Project file: `puffin.yaml`
Illustrative, not final — refine field names in M0 but keep the shape.

```yaml
puffin: 0.1
project: robot-mainboard

boards:
  main:
    kicad_schematic: hw/main/main.kicad_sch
    firmware:
      framework: esp-idf
      target: esp32s3
      mcu: U1
      output: fw/main/main/include/puffin_pins.h

components:
  U1:
    part: espressif/esp32-s3-wroom-1
    board: main
  U2:
    part: example/spi-imu
    board: main

nets:
  IMU_SCK:  [U1.GPIO12, U2.SCK]
  IMU_MOSI: [U1.GPIO11, U2.SDI]
  IMU_MISO: [U1.GPIO13, U2.SDO]
  IMU_CS:   [U1.GPIO10, U2.CS]
  3V3:      [U1.3V3, U2.VDD]
  GND:      [U1.GND, U2.GND]

assignments:            # what each MCU pin is *for* — the firmware-facing intent
  U1:
    spi2:
      sck: GPIO12
      mosi: GPIO11
      miso: GPIO13
      cs.imu: GPIO10

constraints:
  - net: IMU_SCK
    max_freq_hz: 10_000_000

overrides: []           # e.g. {pin: U1.GPIO0, allow: strapping_pin, note: "boot button, intentional"}

intent:                 # free-text design notes the AI can read; never parsed for logic
  U2: "IMU for balance control; read at 400 Hz"
```

### 5.2 Part definition: `parts/<vendor>/<part>.yaml`
```yaml
id: espressif/esp32-s3-wroom-1
kind: mcu
supply: {nominal_v: 3.3}
pins:
  GPIO0:
    functions: [gpio]
    flags: [strapping]
  GPIO12:
    functions: [gpio, spi2.sck, adc]   # use datasheet/IO-mux data
    flags: []
  # ...
peripherals:
  spi2: {signals: [sck, mosi, miso, cs], routable: gpio_matrix}
docs:
  datasheet: docs/esp32-s3-wroom-1.md     # extracted, AI-readable text
  source_url: <official datasheet URL>
timing: {}                                # for peripherals: setup/hold, max clock, modes
```
- Pin functions, flags (strapping, input-only, reserved-for-flash/PSRAM, USB, voltage domain), and timing **must come from the official datasheet / technical reference manual**, with the source cited in the file. Never invent pin data; leave a `TODO(verify)` instead.
- `docs/*.md` are datasheets/manuals translated into clean text/tables so an AI can read and cite them. Provide a documented procedure (and later an MCP tool) for adding new parts from a PDF datasheet.

## 6. Milestones

### M0 — Core graph
- Pydantic models for project + part definitions; load/save round-trips with no diff on unchanged files.
- Edit API: `add_component`, `connect`, `disconnect`, `assign_pin`, `move_pin`, `add_override`, etc. Each returns a structured result (ok / errors / warnings / changed artifacts).
- Validation v1: unknown parts/pins, pin on two conflicting nets, assignment to a pin lacking that function, use of flagged pins without override, assignment ↔ net mismatch.
- CLI: `puffin check`, `puffin show`.
- **Accept:** example project loads, validates, saves byte-identical; every validation rule has a passing and failing test.

### M1 — Firmware generation (deterministic)
- Generator: graph → ESP-IDF header with pin defines per assignment, grouped by peripheral, plus a comment block listing the source net for each pin.
- `puffin gen` writes only if validation has no errors; prints a diff summary.
- **Accept:** golden-file tests; moving one pin in `puffin.yaml` changes exactly the expected lines; output is deterministic across runs.

### M2 — KiCad import
- `puffin import kicad` runs `kicad-cli` netlist export, maps symbols → components (by reference designator) and nets → graph nets.
- Shows a reviewable diff (nets added/removed/changed) before applying. Detects when an imported change breaks an assignment (e.g. IMU_SCK moved from GPIO12 to GPIO14 but `assignments` still says GPIO12) and offers the deterministic fix (update assignment) for confirmation.
- **Accept:** the core demo works end to end: *edit a pin in KiCad → import → graph updated → `puffin gen` → firmware header updated*, with no AI involved.

### M3 — MCP server (bring your own intelligence)
- Tools: `get_project`, `query_pins`, `query_net`, `check`, `propose_edit` (dry run returning diff + validation), `apply_edit`, `generate`, `import_kicad`, `get_part`, `search_docs`, `read_doc_section`.
- Resources: project file, part definitions, extracted docs.
- Bundled prompts/context explaining Puffin's rules to the model (contractor role, never edit generated files, always `propose_edit` before `apply_edit`).
- **Accept:** Claude Code connected to the MCP server can answer "what pins does the IMU use and what's its max SPI clock?" from the docs, and move the IMU CS pin via `propose_edit` → `apply_edit` → `generate`.

### M4 — Web UI
- **Pin map view:** chip outline with pins color-coded by function (GPIO, SPI, I2C, UART, power, ground, flagged/strapping). Click a pin → its net, assignment, flags, datasheet excerpt. Drag an assignment to another legal pin → goes through `propose_edit`, shows the diff, applies on confirm. Illegal targets visibly refused with the reason.
- **Block diagram view:** components as blocks, buses as grouped edges, auto-laid out; read-only in v0 except selecting/inspecting.
- **Diagnostics panel:** live validation results.
- File-watching: external edits to `puffin.yaml` or the KiCad schematic are reflected (import prompt for KiCad).
- **Accept:** the M2 demo can be done entirely from the UI plus KiCad.

### M5 — Hardware-in-the-loop
- **Serial telemetry:** a tiny firmware-side component (ESP-IDF) that streams structured JSON lines (pin states, register reads, test results) over USB serial; `puffin hil listen` and an MCP tool `hil_read` expose them. The AI can write test firmware that reports results this way, which Puffin then treats as observed truth.
- **Logic-analyzer check:** `puffin hil capture --net IMU_SCK,IMU_MOSI,IMU_MISO,IMU_CS` via `sigrok-cli` (any sigrok-supported analyzer), decode SPI, and compare against the part's `timing` + `constraints` (clock rate, mode, setup/hold where measurable). Report pass/fail per check with the measured vs. expected values.
- **Accept:** on a real board, an SPI transaction is captured and checked against the part definition; a deliberately wrong SPI mode is caught and reported.

## 7. Visual identity

Source: the "Puffin" mood board — a palette drawn from Atlantic puffins and Floyd–Steinberg dithered imagery.

**Principle:** desaturated reds/yellows/blues for large surfaces, **saturated accents** reserved for things that need attention or identity.

| Role | Hex | Notes |
|---|---|---|
| Background / ink | `#282226` | Near-black, warm. Primary dark surface. |
| Surface | `#303545` | Slate. Panels, cards. |
| Primary blue | `#31447C` | Selection, links, focus, brand blue. |
| Accent orange | `#EC8F00` | Warnings; highlight; puffin-foot accent. |
| Accent red | `#E72B00` | Errors, conflicts, destructive actions; puffin-beak accent. |
| Cream (approx.) | `#F5DBA0` | Light text on dark / light-theme surface. Sampled from the board; tune. |
| Bone (approx.) | `#D8D2C8` | Secondary text, borders. Sampled from the board; tune. |

Rules:
- **Solid red and orange mean error and warning, and nothing else.** An error or warning always also carries its glyph and outline, so it never relies on color alone. Don't use solid red or orange decoratively anywhere status could be confused.
- The pin map needs ~8–10 distinguishable function categories (families). Build them from the palette colors above, with bg and surface treated as one "dark", and from **ordered dither mixes** of two of them, combined with a **pattern geometry** (Bayer checker or grid, horizontal lines, vertical lines, diagonals, sparse dots, crosshatch). Each family differs from every other in colour pair or pattern, and stays distinguishable in greyscale: by pattern geometry, or, for families sharing a geometry, by lightness. Never rely on color alone: every pin has its label, and flagged pins get a pattern or icon.
- **Red and orange may appear in family swatches only as dithered mixes, never solid:** at most 50% warm share, mixed with dark, blue or bone, and muted (the mix as the eye averages it keeps at most half the chroma of the solid warm color), so no family reads as near-solid red or orange and errors stay the only strong red.
- **Dithering as a fill texture (ordered patterns only):** allowed for family swatches (pin stubs, a strip on a tag, legend chips). It is rendered in screen pixels, pixel-aligned at every zoom level (`image-rendering: pixelated` or equivalent), so there's no moiré. Text never sits on a dithered area; labels stay on solid palette colors and meet WCAG AA. Never dither diffs or diagrams. Floyd–Steinberg is not used for fills: it produces artifacts on flat areas.
- **Floyd–Steinberg dithering** is the illustration texture: splash screen, empty states, part thumbnails, chip illustrations, about page. Do **not** dither data-bearing UI (pin labels, diagrams, diffs) — legibility first.
- Dark theme is the default. Typography: a clean grotesk for UI, a monospace for pins/nets/code.

## 8. AI behavior contract (bundled with the MCP server)

- You are a contractor working from the engineer's design. Ask when intent is ambiguous; don't redesign unasked.
- Never edit generated files. Edit the graph through tools, then regenerate.
- Always `propose_edit` and show the diff before `apply_edit`.
- Cite the doc section for any electrical claim (voltage, timing, pin function). If the docs don't say, say so.
- Treat HIL observations as stronger evidence than your own assumptions.

---

## 9. Quality bar
- Type hints throughout; `ruff` + `mypy --strict` on `puffin/core`.
- Every validation rule, generator, and importer path has tests. Generators use golden files.
- No network access required for core features. Doc extraction may use network only when explicitly invoked.
- Errors are actionable: say what's wrong, where, and the likely fix.

## 10. Dogfood target
The first real project is a **dual-ESP32-S3 robot board** (two MCUs, so cross-board nets and inter-MCU links like UART/SPI must be representable from M0 even if v0 tooling focuses on one board at a time). Put a reduced version in `examples/`. Every feature must make that project faster or safer to build.

## 11. Open decisions (confirm with Eli before/at M0)
1. **Stack:** Python core + FastAPI/Vite web UI (recommended) vs. a native desktop shell (Tauri) later. Recommendation: web UI now; wrap in Tauri only if needed.
2. **Graph format:** YAML (recommended: readable, diffable, comment-friendly) vs. a custom DSL. A DSL can come later as a front end that compiles to the same graph.
3. **Firmware targets after ESP-IDF:** Zephyr devicetree overlay? Arduino? PlatformIO? (Each is just another generator.)
4. **KiCad write-back (v1):** how much graph → schematic sync to support (net labels only vs. symbol/pin changes).
5. **License:** open source (fits the free-library ethos) vs. source-available.
